# Unica Learning landing page - working conventions

Personalized, mailed math and reading workbooks for ages 5 to 14 (Kindergarten to Grade 9). The brand is Unica Learning (D-056). Never write "Pagewise" in new code or copy; only the Supabase project name and old design records still use it. Design truth: `DESIGN.md`. Decision history: `.design/decisions.md`. Workbook pages: `.design/workbooks/DESIGN.md`; what goes into a workbook and when the generator runs: `.design/workbooks/CONTEXT.md` (from Cedric's samples in `.design/workbooks/samples/`).

## Agent rules

- Apply database migrations yourself. Do not ask Savar first. Write the SQL to `supabase/migrations/<yyyymmdd>_<name>.sql`, apply it with the Supabase MCP `apply_migration` (project `cdjobwsyzndtltzfpyqa`), and verify it with `list_migrations` and a probe query. Apply it before the code that needs it ships. Keep migrations additive, so the live code keeps working in between.
- After you apply a migration, run `npm run db:types` and commit the new `src/lib/database.types.ts` in the same PR. The script gives the Supabase CLI the access token in the macOS Keychain item `supabase-pagewise` (or `SUPABASE_ACCESS_TOKEN`), so it works when the CLI is signed in to another account; never run `supabase login`. If the script cannot get the types, write the output of the Supabase MCP `generate_typescript_types` to that file. Never edit the file by hand: put corrections in `src/lib/database.ts` (`ColumnTypes` for jsonb and check-constrained columns, `NullArgs` for function arguments a call sends as null). Do not add `overrideTypes`, `returns<T>()` or `maybeSingle<T>()` to a query: they hide a wrong column name from the build.
- Open a pull request yourself when you finish building something. Do not ask first. Use a branch named `site/<topic>`, from a worktree based on `origin/main`. Merging to `main` deploys production, so leave the merge to Savar unless he asks.
- Never switch branches in the main checkout. Other agents work in parallel worktrees (`git worktree list`).
- All design work goes through `/design`. Mockup rounds live in `.design/experiments/r<n>/`, with a `manifest.json`.
- Images under `.design/` (png, jpg, jpeg, webp, gif, mp4, mov, pdf) are stored in Git LFS (`.gitattributes`). On a new machine, run `git lfs install` once before you clone or pull; without it, the images check out as small pointer text files. Keep images the site ships (`src/`, `public/`) out of LFS: Vercel builds with LFS off. If git lists `.design` images as modified after a merge, a branch committed them before LFS: run `git add --renormalize .design` and commit.
- Use the Aside CLI (`aside`) as the browser for every browser task in this project: browser checks, screenshots, end-to-end runs and email checks. Do not use Playwright, Puppeteer or another headless browser. The one exception is the workbook renderer's print engine (`src/lib/print-engine-chromium.ts`, #309), which drives headless Chromium with `puppeteer-core` to print workbook pages; it is not a browser check. Use `aside exec "<task>"` for a simple task and `aside repl` for DOM checks and screenshots; run `aside guide repl` once before the first `aside repl`. Use `--account u0`.
- Done gate: `npm test && npx eslint src && npm run build`, then check the change in the browser (Aside) with `npm run dev`. `npm run lint` also scans `.design-sync/previews/`, which has old errors. Vitest does not typecheck; `npm run build` does.
- Tests (Vitest, `src/**/*.test.ts`) use only a module's public interface. The assessment core (`src/lib/assessment`, imported as `@/lib/assessment`) is pure TypeScript with no network, database, clock or `Math.random`. The test attempt module (`src/lib/test-attempt.ts`, spec #144) owns a child's test behind one store seam: its tests use the in-memory store (`src/lib/test-attempt-memory.ts`) and pass in the clock. The report-loading module (`src/lib/report-loading.ts`, spec #145) reads the report inputs for the report job and the report view for the report page, the admin report view and the report email, behind one reader seam (the parent's session, the admin's session, or the secret key): its tests and the report job's tests use the in-memory reader (`src/lib/report-loading-memory.ts`). The workbook store (`src/lib/workbook-content.ts`, #299) reads and writes whole workbooks behind a store seam: its tests run the Supabase store (`src/lib/workbook-store.ts`) and the in-memory store (`src/lib/workbook-store-memory.ts`) through the same cases. The workbook renderer (`src/lib/workbook-render.ts`, #309) prints through a print engine seam: its tests use the fake engine (`src/lib/print-engine-fake.ts`); `src/lib/print-engine-chromium.test.ts` renders with real Chromium where one is found. The saved-card module (`src/lib/saved-card.ts`, D-106) decides whether a child's report card is saved, behind a store seam (`card_setups`) and a provider seam (Stripe): its tests use the in-memory seams (`src/lib/saved-card-memory.ts`). The board history (`src/lib/board-history.ts`, #320) is the log of "Our board" on the desk (Maya's batches, the child's strokes, the pen) with its draft behind a draft store seam: its tests use the in-memory store (`src/lib/board-history-memory.ts`) and pass in the time of each change. One tab writes a board (`src/lib/board-tab.ts`): it holds a Web Lock (where there are none, a storage lease with no expiry, let go on `pagehide` and taken from a tab that does not answer only by "Use it here"); another tab shows the board read-only with "Use it here"; its tests use the in-memory locks, channel and timers of the same file. The board session (`src/lib/board-session.ts`) owns one tab's stroke in progress, holding the board and the ink kept when it moves away; every way out of holding goes through `endHolding`; its tests drive a real board tab on the same in-memory seams. The tests of these modules are the pattern for later ones.
- Copy rules in `DESIGN.md` are binding: no proof we do not have, no performance claims, and no competitor brand names outside `/resources` and `/blog` (compare with categories such as learning centres, D-064; `/resources` guides and `/blog` posts may name them with cited, dated facts, D-074, D-152).
- Blog (`/blog`, D-152): one post per file in `src/content/blog/<slug>.tsx`, registered in `src/lib/blog.ts`; writing rules in `docs/blog-style.md` (checked by `src/lib/blog.test.ts`); topic queue in `docs/blog-topics.md`. The cloud routine "Unica weekly blog" runs `docs/blog-automation.md` every Sunday and pushes one post on a `claude/blog-<slug>` branch. The GitHub Actions workflow `Blog publish` (`.github/workflows/blog-publish.yml`) checks with `scripts/blog-publish-guard.mjs` that the branch only adds or fixes a post, merges it into `main`, runs the done gate and pushes `main`. Never name a branch `claude/blog-*` for any other work; a name ending in `-dryrun` runs the checks without the push.
- Use plain language in all customer text. Keep development notes and draft labels out of public pages. Give provider names only in the privacy disclosure, with a plain explanation.
