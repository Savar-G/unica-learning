# Parent dashboard release

`PARENT_DASHBOARD_ENABLED` is a server release switch (spec #544, #551). Leave it unset. While it is unset, only families marked in `public.test_accounts` and users listed in `public.admin_users` get the dashboard, and every other family gets today's Parent home. The server reads those marks on each request. A browser cannot supply its own mark.

Only the exact value `on` opens the dashboard to every family. Set it in the server environment and redeploy, and do this only after Savar approves on the one review page (D-249). Remove the value and redeploy to close it again.

## What the switch controls

- `src/lib/parent-dashboard-access.ts` is the check. `parentDashboard()` in `src/lib/parent-dashboard-server.ts` calls it, once per request, for the layout and the home page.
- `src/app/(product)/account/(dashboard)/layout.tsx` adds the frame. For a family the switch does not open to, it returns the page alone. A failed read of the dashboard's facts also gives today's Parent home.
- `src/app/(product)/account/(dashboard)/parent-home.golden.html` is today's Parent home, written from the page before the dashboard existed. `page.test.ts` compares a normal family's page with it, byte for byte.
- `/account/settings` is the Account tab. Everyone else goes back to `/account`, which has the same links.

The pages in `(dashboard)` keep their addresses, because a route group is not in the URL. The test, its start screen and the first sign-in (`/account/test`, `/account/start`, `/account/finish`) stay outside the folder, so they never show the frame. The desk lock, the desk guard and the proxy's 423 apply as before: `src/proxy.ts` matches `/account/:path*`, and the guard is in the layout above.

## Billing on the Account tab (#554)

`src/lib/billing.ts` holds the rules, behind a store seam (`card_setups`, read with the secret key and filtered on the signed-in parent) and a provider seam (Stripe).

- Plans come from `child_plan_states`. A load of the Account tab fills a missing row with `fillChildPlan`. The frame reads the same rows through the parent view, so a family with no row yet shows its tabs as `unknown` for that one load.
- Invoices load live, on this page only, from every Customer of the family, on every page of each list. If any read fails, none of the list shows: a part of it would read as all of it.
- "Update card" opens Stripe Checkout in setup mode, for cards only (`allowed_payment_method_types`; Stripe refuses `payment_method_types`, checked in test mode on 5 November 2026). `/api/account/card-update/return` checks that the session names this parent's row and that row's customer, then sets the new card as the Customer's default (`invoice_settings`) and as the default of each subscription that can still charge. A plan that has not started has no subscription: `startPlan` uses the row's newest card, else the Customer's default when it is a card, else the customer's newest card. The old card stays on the Customer.
- Only the newest update counts. `public.child_card_updates` holds one row per child with the session of the newest update, its time at Stripe and its card's Stripe id. The order is by when Stripe's page opened, not by when the parent finished it: of two pages open at once, the one opened later wins (the same second: the higher id). A return of the same session or an older one with nothing to repair changes nothing and shows the normal page with no notice, so a browser history entry or another tab cannot bring an older card back.
- Stripe follows the row (`src/lib/card-reconcile.ts`). A client timeout leaves a Stripe request's outcome unknown, and the request can land later, so no lock can order the writes. Each path compares Stripe with the row's newest card and writes only what differs: the plan's default first, as a charge uses it, then the Customer's.
  - The return records its card with `record_card_update`, which sets `needs_repair`, then brings Stripe to the row's newest card, whichever return it is. `settle_card_update` then clears the flag, or hands the caller a newer card to compare with. A refused write of an older card goes on to the newer one.
  - The webhook does the same on `customer.subscription.created` and `customer.subscription.updated` (`docs/stripe-webhook.md`).
  - The sweep does the same in the `/api/reminders` run, every 15 minutes (`src/lib/card-sweep-server.ts`). It looks at each row whose card changed in the last 7 days, is flagged, has an open plan start or has a pending plan email, the row looked at longest ago first. It runs beside the emails. From the start of the run: no new row after 25 seconds, no Stripe write and no email after 30 (each has a 15-second limit), and all its work ends at 45, by one signal that goes to every Stripe call, database call and email in it. The monthly emails' work still ends at 50, and the route's limit is 60. A row cut off at 45 stays due: a stopped write or email has an unknown outcome, and the next run reads Stripe and the claim again. Its emails go through the run's one paced transport, with the reminders and Maya's safety alerts: requests run one after another, at least 600 ms between their actual starts. `?dry=1` counts these rows as `cards` and writes nothing. It is the only path that sees a late write to the Customer, as that write raises no event we listen to.
  - Only a read that shows Stripe on the row's card clears `needs_repair`. A comparison that fails or that cannot confirm sets it, so the sweep goes on after the 7 days.
- What a parent sees. `updated`: Stripe answered each of our writes, and this card is the row's newest. `unconfirmed`: a write's outcome is unknown, or our time ran out, so the card is recorded and the sweep writes it. `failed`: nothing was recorded, or Stripe refused the card. `stale` (no notice): nothing changed for this card.
- The longest time a stray write can stay. A late write to a plan raises an event, and the webhook corrects it in seconds. If that event is lost or the webhook is down, the next sweep corrects it: up to 15 minutes, plus the run's time. If the sweep's run also fails, the next run does it. A late write to the Customer changes no charge of a running plan, as the plan's own default is what a charge uses, and the next plan start reads the row.
- A plan start (`startPlan`, `src/lib/stripe.ts`) has one durable record in `public.plan_starts`, one key per card setup and generation. The record is never cleared.
- An open plan start refuses family deletion in the database, after the start route releases its card hold. The self-serve check, delete hold and request, the older request, the admin request, and both worker claims return `plan_start`. The worker keeps the family and reports the count. The parent sees that the team must finish the start first, and the existing deletion alert tells the team. A resolved or team-closed record removes this refusal.
- An older deployment could queue deletion before an open start closed. `card_recovery_rows` exposes only that family's existing open start. The webhook, sweep and admin close read Stripe and resolve or close the record. They do not change cards or send a parent confirmation. The table's trigger permits only that open record's resolution and team alert; every other family write stays fenced. The alert names the queued deletion. Both deletion worker phases read `family_deletion_start_customers`, cancel any subscription that can still charge, and read Stripe again before they remove data. A failed read or cancellation keeps the family for a retry. The old `card_check_rows` reader stays fenced for older deployments.
- Plan confirmation emails use `(card setup, generation)` on `plan_starts`. Generation 0 reads the old `workbook_emails` row at workbook number 0. Generation 1 also respects that old claim during deployment. Later generations have their own claims. Before a send, the time check runs after the database reads and claim and after the transport wait. A claim whose send did not start returns without consuming an attempt, so the next sweep can send it.
  - `admit_plan_start` is the one way to a create call, under the child's row lock. It opens a generation only when the one before it is closed. Otherwise it answers the newest record. So a press that read an empty list before another press finished finds that record and answers `already`, and a press beside an open record gets its key and card, as Stripe refuses a key with other fields.
  - Stripe answered: the record closes as `started`. Stripe refused: it closes as `refused`, and the next press opens a new generation. Unknown (a timeout, a lost connection, a 5xx, a 409, a 429): the answer is `unconfirmed`, and the record stays open.
  - An open record closes when its subscription is found, by `metadata.start_key`. A different subscription leaves the original request unresolved in the start, webhook, sweep and admin-close paths. The database refuses an open record's transition to `other`, before and after a deletion fence, including calls from an older deployment. Recovery waits and alerts the team after 24 hours. The next press gets the matching plan's answer, so the start route sends the email. The webhook and the sweep correct the card, close the record and send the email; they leave a record younger than 60 seconds, as its start may still be answering.
  - A closed `started` record answers `already`. A new generation opens only when no plan is running and the record's plan reads as over in Stripe's whole list. A list without that plan proves nothing, so it also answers `already`.
  - Time closes nothing. At 23 hours a press stops retrying and answers `unconfirmed`. At 24 hours Stripe may forget the key, but that does not prove that the first request ended. So with no subscription found the record stays open, the sweep goes on looking, the team gets one alert through the email delivery module (`src/lib/card-plan-alert.ts`), and a press answers `needs_team`. The card under `/admin/next-steps` shows it, with the button "I checked Stripe: close this start" and a confirmation. Only that button closes the record (`endStuckPlanStart`, `team_end_plan_start`). It reads Stripe first: a plan it finds closes the record as started, and a failed read closes nothing. If the subscription shows up first, it resolves as usual.
  - The confirmation email has its own state on the record (`email_state`). A closed `started` record with a plan still on is `pending`. A refused or busy send stays pending for the next sweep. An unknown outcome is final and nothing sends it again. After a busy send, the sweep reads the email's claim: `sent` and `unknown` are final, and a claim held for 10 minutes counts as unknown, as the dispatch's check does. The sweep waits 60 seconds after a press closed its own record, as the start route is sending the email.
  - A running subscription always answers `already`.
- Known limits. The row is the truth: a default changed by hand in Stripe's dashboard goes back to the row's card, at the next subscription event or sweep. To change a card, have the parent use "Update card". A card that Stripe keeps refusing stays flagged and is tried again in each sweep, until a newer card arrives; find these with `needs_repair` and an old `updated_at`.
- Probes: `supabase/tests/plan_starts.sql`, `supabase/tests/card_row_reconcile.sql` and `supabase/tests/child_card_updates.sql`, through the Supabase MCP `execute_sql`; a run ends with `PROBE_OK` and rolls back.
- Cancel stays on `/account/plan` (D-222).
- Pause (#559) and paid Restart (#546) use the existing Account and Plan child cards. Pending requests keep a recovery action after reload. The release stays off. Supported states, the classic paid Pause refusal, durable holds and parent acceptance steps are in `docs/plan-controls.md`.
- Both card routes answer only to a family the switch opens to, and every other family keeps today's pages.
- Stored plans change only through `docs/stripe-webhook.md`. Set up that endpoint before families see this page, or a filled row goes stale.

## Child details on the Account tab (#555)

`src/components/account-child-details.tsx` shows one section per child: the first name, the school grade and the learning card. The learning card's questions stay at `/account/learning/<child>` with their route, `/api/account/learning`, which rebuilds the profiles after a save. A grade change goes through the support email.

`PATCH /api/account/children/<id>` changes the first name. It answers only to a family the switch opens to, and answers not found to every other family and for another family's child. Parents have no update right on `first_name`, so the server's key writes it through the service-only function `rename_child` (migration `child_rename`), which keeps it to the parent's own child, and the family write fence still applies. It takes the name by the signup rule (`cleanFirstName`).

The rename refuses while the child has an active workbook run. A kept page prints the name in its id, and a resume with another name fails the run. `rename_child` checks the runs and writes the name in one transaction under the child's row lock, and `start_workbook_run` takes that same lock first, so no run starts between the check and the write. A run is active by the app's rule for a stopped run (`runState`, `STALE_SECONDS` in `src/lib/workbook-job.ts`): a queued run for the Mac waits however long it takes, and any other queued or running run is active until it has had no heartbeat for 6 minutes. `rename_child` locks the child's queued and running runs while it decides, so it waits for a resume being made and then sees its fresh heartbeat. A stopped run whose status still says running never blocks a rename: the rename ends it in the same transaction, as `fail_workbook_run` does (failed, the reason "The child's name changed while this workbook was stopped. Prepare it again.", no lease, a `run-failed` audit row), so its old lease writes nothing more and it cannot be taken up again (migration `child_rename_stops_runs`). The admin run page shows that reason, and the next "Prepare next workbook" starts a new run with the new name.

Each rename keeps the name before it in `children.former_names` (oldest first, each once, at most 20; only `rename_child` writes it, and it goes with the child row). After 20, the route answers `too_many_names` and the parent emails support. The call note writer (`src/lib/maya-call-note.ts`) hides the former names in every form it hides the name now, so a note written after a rename keeps none of them and sends none to the AI. `supabase/tests/child_rename.sql` checks the function in a rolled-back transaction, and `supabase/tests/child_rename_locks.sh` checks the shared lock with two connections.

What a name change updates, because these read `children.first_name` when they show or send: the dashboard, the report and report email (the stored report holds a token), Maya's notes and transcripts (stored with `{child}`), the desk and Maya's next request, reminders and workbook emails, and the next workbook.

What it does not update: a workbook draft or shipped workbook already made (its pages, page ids, images and PDF print the old name, so an unshipped draft ships with the old name unless an admin makes a new one), and an email already sent, with its copy in `email_copies`. A call's stored trace (admins only) hides only the exact name the child had during the call, as before; the note hides every name.

## The monthly summary email (#563)

One email per family per month, with a link to each child's Overview and no attachment. `src/lib/monthly-summary-email.ts` holds the rules, `src/lib/monthly-summary-email-store.ts` the reads and the claims, and the `/api/reminders` run sends it after the other emails, on the same spaced transport (one send every 600 ms). `?dry=1` counts it as `monthly` and sends nothing.

- Who: only a family the switch opens to, through `parentDashboardAccess`, as the rest of the dashboard reads it. While the switch is off, that is test families and admins, with their real addresses. A failed read of a mark counts as not marked. An address on a domain that cannot get email (`canGetEmail`) is left out. A family with no confirmed delivery has no summary, so it gets no email.
- Which children: each child whose summary the Overview offers. `src/lib/monthly-summary-offer.ts` is the one rule; `readOverview` and the email both call it, in family time (`src/lib/family-time.ts`). A child with an ended plan still counts, because the Overview still offers the summary.
- When: from the 1st of the month at 7 a.m. family time to the end of the 7th. It names the month that just ended. After the 7th, a family with no email that month waits for the next month. The store reads nothing on UTC days that no window touches (the 9th to the 27th).
- Once: the send key is (parent, month), in `email_log.summary_month` (the first day of that month), with a unique index. A refused send retries up to `MAX_SEND_ATTEMPTS` times. An unknown outcome stays claimed, and nothing sends it again. A claim that fails stops that family only. A run sends at most 20.
- Time: the monthly work ends 50 seconds after the run began, inside the 60-second limit. One email needs 24 seconds: 5 for the claim, which aborts then, and 19 for the send and its writes. With less time left, the run starts no read and no claim, and an aborted read stops the monthly step (`outOfTime`); the next run does the rest. A claim that ends with under 19 seconds left is given back without counting an attempt (`released`): a first claim's row is deleted, and a retry's row is failed again at its old count. If the release fails (`stuck`), or an aborted claim's write lands after its release looked, the row stays claimed and nothing sends that email: one lost email, never two. The writes after a send have no abort, so a database that hangs there can still reach the limit; the row then stays claimed and the email is not sent twice.
- Its own unsubscribe: kind `monthly_summary_unsubscribe`, one row per parent. It stops only this email, and no other unsubscribe stops it. The page is `/unsubscribe`, with its own words for this email.
- `public.email_copies` keeps what was sent, with the link tokens hidden. The admin dashboard lists both kinds. Clicks are not counted, so the admin shows no click rate for this email.

A signed-out parent who opens the link goes to sign-in and then back to the same child (`signInPath`). The email says nothing about results: no level, no percent right and no comparison. It names the child, never she or her.
