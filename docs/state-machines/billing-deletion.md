## Top findings

1. **A failed or uncertain cancel leaves a permanent dead end** (`src/lib/parent-plan-server.ts:77-92`, `src/lib/stripe.ts:376`, `supabase/migrations/20261105234500_plan_controls.sql` `admit_plan_cancel` / `finish_plan_control`). `cancelFamilyPlan` admits an `open` `plan_control_operations` row plus a no-expiry `family_card_operations` hold, then calls `cancelPlan`. If `cancelPlan` throws (even on its first READ of the subscription list, before any write) nothing calls `finishControl`. The op stays `open`. A second Cancel gets `admit_plan_cancel` = null ("pending", 409). Nothing in `src/` calls `finish_plan_control` except the Pause path and the Cancel happy path. No admin screen, no sweep, no recovery for Cancel (Pause has `recover`, Cancel has none). While open: `assert_plan_workbook_allowed` raises `plan_control_pending` for every new workbook run and shipment of that child; Pause/Restart report "pending"; family deletion answers `busy` and retention skips the family (the hold has no time expiry). Parent sees "Cancellation is not confirmed. Please email" (`src/components/account-billing.tsx:48`, `parent-plan-view.tsx:41`). Doc admits it (`docs/plan-controls.md` "A pending cancellation currently needs a team check"), but the code cannot tell "read failed, nothing sent" from "write sent, answer lost".
2. **Admin "Start free month" button maps four real error codes to the wrong sentence** (`src/components/start-plan.tsx:10-19, 38`). `ERRORS` lacks `restart_required`, `wrong_mode`, `family_unavailable`, `payment_refused`, `not_ended`; all fall to `ERRORS.failed` = "Stripe could not start the plan. Check Stripe before trying again." Reachable: an admin presses the button for a card whose plan already ended (`restart_required`, `src/lib/stripe.ts:269`), or while a parent Restart is open (`wrong_mode`, `stripe.ts:258`), or during a family deletion (`family_unavailable`, route `start/route.ts:47`). Also the button is rendered for EVERY card with a saved card and a customer (`src/components/admin-records.tsx:38`), even after the plan started, so a reload offers "start" again and answers `already`.
3. **Four different definitions of "a subscription is running"** (see "Running-plan definition" below). Same today, diverge on any new Stripe status. Money paths use different ones: `parentPlan`/`cancelPlan`/`convergeCard` use `RUNNING_PLAN` (6 statuses, `parent-plan.ts:41`); `startPlan`/`pressStep`/pause/delete-recovery use `planNotOver` (everything except 2, `card-reconcile.ts:45`); `runningPlans` (family delete, `stripe.ts:410`) is the same complement; retention uses `LIVE` and treats an unknown status as "unknown, keep" (`assessment/retention.ts:56`). A new status makes a start refuse (`already`), the parent page show `ended`, cancel say `no_plan`, and delete stop it.
4. **Plan gate and screens use three clocks/sources for "ending"**: gate closes on date in code (`plan-access.ts:41-45`, now vs `ends_at`) while the stored kind stays `ending` until Stripe's `customer.subscription.deleted` arrives. In that window the closed note says "has ended ... use Restart plan" (`plan-closed-note.tsx:36`) but the Restart button only renders for stored kind `ended` (`account-billing.tsx:52`, `parent-plan-view.tsx:45`). Window is seconds if the webhook works, up to ~24h15m if lost (the `ending` row is re-read daily). Low frequency, real "button that does not exist".
5. **Cancel does not write plan state; the screen goes stale or "unknown" after a successful cancel.** `src/app/api/account/plan/cancel/route.ts` only calls `cancelFamilyPlan`. `finish_plan_control('applied')` sets `child_plan_controls.cancelled = true` at once, but the stored `child_plan_states` row still says `paying`/`free_month` until a webhook. `adjustedPlan` (`plan-controls-server.ts:155`) returns `unknown` for a stored paying/free_month plan with `cancelled` true, so the Account tab shows "We cannot load this plan now" (`plan-text.tsx:25`) after a successful cancel until the webhook lands (daily re-read is the fallback). If Stripe later un-cancels (support action in the Dashboard), `cancelled` stays true forever (only a paid Restart clears it, trigger `record_paid_restart`): Pause shows "pending" and the plan reads `unknown` for a running plan.
6. **Dead state `other` is still threaded through 8 TS files and 6 SQL objects.** No code writes `state = 'other'` any more: `fence_plan_start_write` raises `plan_start_unresolved` for open -> other (`20261105210902_plan_start_recovery_matching_key.sql:10`). Still in: CHECK constraint, `finish_plan_start`, `PlanStartState`/`PlanStartOutcome` (`card-reconcile.ts:81,112`), `pressStep` (`:340`), `startPlan` (`stripe.ts:269,278`), `familyHasPlanHistory` (`plan-access.ts:103`), child-delete pending query (`20261105_child_delete.sql:100`), scan-reminder program (`20261107073840_workbook_scan_reminder_episodes.sql:320`), `admit_plan_start_terms`. Every "is the start finished" list is a hand-copied string list (`('started','other','refused','team_ended')` in 3 SQL files and `["open","started","other"]` in TS).
7. **Plan start confirmation email has two parallel state machines on one row** (`plan_starts.email_state` none/pending/sent/unknown AND `plan_starts.email_send_status` null/sending/sent/failed/unknown). The route's own send (`start/route.ts:84`, `sendPlanStartEmail`) only moves `email_send_status`; `email_state` stays `pending` until a later sweep visit runs `tellParent` -> `planEmailClaim` -> `note_plan_start_email` (`card-reconcile.ts:376-395`, `workbook-email-server.ts:135-152`). Every started plan therefore costs one more sweep visit and depends on a busy-send reconcile to reach `sent`. A stuck `sending` claim is converted to `unknown` by an app-side 10 minute rule (`SENDING_STOPPED_MS`), not in SQL. Team alert has the same shape: `team_alert_state = 'sending'` has no timeout, so a worker that dies mid-send leaves the alert claimed forever and the team never hears (`card-reconcile.ts:359`, `plan_starts.sql claim_plan_start_alert`).
8. **Stored plan row "event time" for a start comes from the app clock** (`applyPlanStart`, `plan-state.ts:115-121`, fed by `Date.now()` at `start/route.ts:51` and `plan-controls-server.ts:119`) although the file header says "App clocks play no part". `applyPlanEvent` skips any event whose Stripe time is older than the row's `event_at` (`plan-state.ts:103`). With app clock ahead of Stripe by N seconds, a real change inside that N seconds (for example a cancel right after a start) is skipped as "older" until the daily re-read. The re-read path was designed around this (`plan-state.ts:158-170`), the start path was not. (Impact bounded by clock skew; unverified in production.)

Other notable: the `/api/admin/cards/[id]/start` route leaves the card-operation hold (no expiry) when `startPlan` throws, including after a definite Stripe refusal of an initial start where the record is already closed `refused` (`stripe.ts:296-305` rethrows after `closeRecord`; route catch at `start/route.ts:57` never calls `endCardOperation`). Family self-delete answers `busy` and retention skips the family until an admin retries.
