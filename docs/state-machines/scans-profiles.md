## Top findings

1. **Dead-end marking job.** `scan_marking_command` `pause` with status `attempts` sets the job to `finished` (20261105_scan_marking.sql, `pause` branch; same text in 20261106_scan_marking_sheet_check.sql). Two failed model calls (dispatches reaches 2) hit this. Its items keep `observation.state='pending'`, `model` NULL and certainty `not-read`. `finished` jobs are excluded from recovery (`coalesce(j.state,'queued')<>'finished'` in `recover_scan_marking_oldest`), and `admin_scan_team_queue` requires `model is not null or certainty<>'not-read'`, so the team never sees them. Only a new photo (delete and retake) revives it. The parent sees "Not marked yet" forever (`itemLabel`, src/lib/scan-marking.ts:321-333). Not reproduced; derived from the SQL.
2. **Only `budget` is ever shown as a job reason.** `blocked_reason` has 5 values (`off`,`budget`,`price-unverified`,`attempts`,`pending`) but only `held === "budget"` reaches a screen (src/lib/scan-marking-server.ts:80,87; src/components/scan-marking-results.tsx:21). The other four show as "Your page is not marked yet" / "Some answers are not marked yet". The admin scan page dumps the raw job as JSON (admin/scans/[id]/page.tsx:70). Lying/blank screens for stuck jobs.
3. **Migration order trap.** Filename order puts `20261106_scan_mark_changes.sql` BEFORE `20261106_scan_marking_sheet_check.sql` (`_` sorts before `i`). The live registry has the opposite order: sheet_check 20261106003403, then mark_changes 20261106034512, then page_history 20261106170640. Live result is a 3-layer wrapper chain (`scan_marking_command` -> `scan_marking_saved_command` -> `scan_marking_automatic_command`, verified by function-body probe). Replaying the repo files in filename order would make sheet_check's `create or replace` overwrite the mark_changes wrapper and break the rename chain. Also two live migrations are missing from the repo: `20261109030823_scan_cleanup_timeout` and `20261109035739_scan_progress_families`.
4. **"Waits for our team" rule exists in 5 places.** TS `waitsForTeam` (scan-marking.ts:317), SQL `admin_scan_team_queue` and `admin_set_scan_mark` (20261107213302_scan_team_mark_followups.sql), TS `teamMarkNeedsPhoto` (scan-team-marks.ts:26) vs SQL `no_photo` branch (20261107220421), and the partial index `scan_marking_items_waiting` (20261107204619, predicate does not include the model/certainty part). The "page item is finished" rule is also copied: TS `isTerminal`/`pageCompletion` (scan-observation.ts:274,298) and SQL inside `parent_explanation_command` ("Match pageCompletion", 20261107213302). A third reader is the SQL trigger `capture_workbook_scan_resolution` (live function, reads old/new observation state).
5. **"Is a photo active" rule has 4 copies with 2 different numbers.** SQL `scan_photo_is_active` (pending counts only for 23h30m), `isActive` in scan-crops-store.ts:12 (23.5h), but `active()` in scan-stack-server.ts:19 and `scanView` in scan-photo-server.ts:54 use 24h. A pending photo aged 23.5-24h shows in the stack as "Checking" and `scanView` says live, while the DB treats it as terminal (`begin_scan_calibration` returns `terminal`, `expire_scan_photos` expires it).
6. **Marking rebuild wipes AI findings.** `rebuildChildNow` in scan-marking-server.ts:69 calls `rebuildChildProfile` with no `ai` and no `keepFindings`, so each marking/recovery rebuild stores a facts-only profile (`ai: null`, child-profile.ts:434). Findings from a Maya or report rebuild are dropped until the next AI-enabled rebuild. Header says this is by design for AI-off builds; here the cause is the call site, not AI being off. Planner/Maya in between read no findings.
7. **"Profile pending" is encoded as arithmetic.** `save_marked_child_profile` writes `profile_revision = p_marking_revision - 1` when skill states failed (20261106_scan_mark_changes.sql). The recovery list then keeps the child via `profile_revision < revision`. It works but nobody can read the state from the data; a column or enum would say it.
8. **Calibration "checking" can hang with no one driving it.** The check job is started only by the browser asking the preview route; `stackCheck` returns `checking` for no row or `running` regardless of lease age (scan-stack-server.ts:28). A closed tab leaves "Checking" until the parent returns (attempt cap 5 only counts when someone calls begin again).

### 1. Scan photo lifecycle
- Entity / storage: `public.scan_photos` (20261102_scan_page_photos.sql): `state` check in (`reserved`,`processing`,`pending`,`saved`,`deleted`,`expired`,`rejected`); `sent_at` (added 20261105_scan_stack.sql); `terminal_at`; `lease_until`; `expires_at` (90 days); `created_at`; `reserved_bytes`/`stored_bytes`. Storage bucket `scan-photos` (object `photo.jpg` plus derived files).
- States: reserved (slot booked, no upload) -> processing (upload under lease) -> pending (stored, not saved) -> saved (kept) ; terminal: deleted / expired / rejected. Overlay: `sent_at` null/non-null on a saved photo ("sent for marking"). Terminal rows keep bytes until Storage confirms removal (`reserved_bytes`/`stored_bytes` > 0 = cleanup owed). "Active" is a derived predicate, not a state: saved and not past expires_at, or pending younger than 23h30m.
- Transitions (all SQL, service role):
  - none -> reserved: `admit_scan_photo` (POST /api/account/scans). Re-admit of the same id answers its current state. Latest def: 20261105_scan_marking.sql (adds the unfinished-marking queue cap).
  - reserved -> processing: `start_scan_photo` (PUT /api/account/scans/[id]); latest def 20261105_scan_marking.sql (uses `scan_active_jobs`).
  - processing: `identify_scan_photo` freezes page_id/workbook_id/printed_revision/width/height (no state change); `finish_scan_photo` -> pending.
  - pending -> saved: `change_scan_photo(save)` (POST /api/account/scans/[id]); requires created_at > now-24h.
  - any non-terminal -> deleted / rejected: `change_scan_photo(delete|reject)` (DELETE route; PUT failure path calls `reject`, route.ts:42).
  - reserved -> rejected: `release_scan_photo` (20261105_scan_release.sql; POST .../release).
  - -> expired: `expire_scan_photos()` pg_cron `scan-photo-expiry` every 5 min (latest def 20261102_scan_photo_frozen_expiry.sql); also called inside `/api/scan-cleanup` (scan-photo-server.ts:73). Rules: expires_at passed; or not saved and older than 23h30m; or reserved/processing with lease over.
  - saved -> saved+sent: `send_scan_photos` (20261105_scan_sheet_check.sql version; POST /api/account/scans/send).
  - terminal bytes -> 0: `reconcile_scan_cleanup` after Storage removal (`cleanupScanPhoto`, pg_cron `scan-photo-cleanup` every 15 min -> /api/scan-cleanup).
  - `recover_scan_photo` (GET route) finishes an upload whose Storage object exists but whose finish call was lost.
- Where rules live: SQL functions above are the single authority for transitions. The `active` predicate is copied in 4 places (see Top finding 5). Files that mention the photo state strings in src (excluding tests): 12 files reference `scan_photos`; the state literals appear in scan-stack-server.ts, scan-stack.ts, scan-photo-server.ts, scan-crops-store.ts, scan-marking-server.ts, scan-marking-store.ts, scan-history.ts, scan-send-marking.ts, scan-image-delivery.ts, scan-team-marks.ts, components/scan-pages.tsx, components/scan-mark-change.tsx and the account scans routes (rg count above).

Transitions are guarded in RPCs under `pg_advisory_xact_lock('scan:'||parent)` plus a row lock. NOT enforced: no check that `sent_at` implies state saved at write time; no check on legal state edges (any RPC could write any state; trigger only guards the expiry/cleanup exemption).
- Impossible / unhandled states: `sent_at` set on a photo that later becomes deleted/expired is legal and common (jobs and items keep the reference; `send_scan_photos` return filters `state='saved'`). `pending` older than 24h shown "expired" by `scanView` while DB still says pending until the 5-minute cron. `admit_scan_photo` answers `reserved` for a reservation whose lease already lapsed (up to 5 minutes until the cron), then `start_scan_photo` answers `expired`; the route maps any non-`reserved/processing/pending/saved` admit answer to HTTP 429 (route.ts:15) including `deleted`/`expired`/`rejected`, so a "limit" status code carries an "ended" meaning (client handles via ENDED list in components/scan-pages.tsx:29).

Family advisory lock serialises admit/start/identify/send; unique index stops two active photos for a page (identify answers `duplicate` on unique_violation); expiry takes parent share lock before photo (20261102_scan_photo_frozen_expiry.sql comment). - What the user sees: parent stack tiles: adding / checking / ready / saved / refused / unavailable / sent (components/scan-pages.tsx:55 STATUS_WORDS; derivation scan-stack.ts:142-154). Upload refusals as refused uploads (scan-stack.ts:105 table). Sent tile: "Sent for marking." plus link to results only when marking is open, else "Marking is not ready yet. The page waits here." ### 5. Marking job (scan_marking_jobs)
- Entity / storage: `public.scan_marking_jobs` (20261105_scan_marking.sql): `photo_id` PK; `state` check in (`queued`,`running`,`extracted`,`finished`); `lease_token`,`lease_until` (180 s); `dispatches` 0..2; `extraction` jsonb (null/non-null encodes "model answered"); `blocked_reason` check in (`off`,`budget`,`price-unverified`,`attempts`,`pending`) or null; `frame_hash`; `item_versions`; `model`,`prompt`.
- States: (no row) -> queued -> running -> extracted -> finished; queued with `blocked_reason` = paused. `running` vs `extracted` is also readable from `extraction is null`. `finished` conflates success and `attempts` exhaustion (blocked_reason attempts).
- Transitions (all inside `scan_marking_command`; live chain command -> saved_command -> automatic_command; automatic def = 20261106_scan_marking_sheet_check.sql):
  - `claim`: none/queued/expired lease -> running (or extracted if extraction exists); sets lease 180 s, clears blocked_reason; returns `busy` when lease live or slot taken; `unavailable` when finished or hash changed.
  - `admit`: reserves budget, dispatches+1; refusals `terminal`, `budget`, `price-unverified`, `attempts`.
  - `extract`: running -> extracted (stores model output).
  - `apply`: writes item observations (version +1), bumps child marking revision.
  - `pause(status)`: -> queued with blocked_reason, lease cleared; status `attempts` -> `finished`.
  - `finish`: -> finished, lease null.
  - WHO: `runScanMarking` (src/lib/scan-marking.ts:243) called by `processScanMarking` from Send `after()`, the recovery cron, and POST /api/account/scans/[id]/marking (parent can re-trigger; maxDuration 180).
- Where rules live: SQL `scan_marking_command` (3 wrapped versions, ~13k chars automatic), TS `runScanMarking` (status vocabulary `MarkingStatus`: finished/pending/busy/terminal/unavailable/off/budget/price-unverified/attempts, scan-marking.ts:55), `MarkingStore` seam, `scanMarkingStore` (scan-marking-store.ts). `blocked_reason` values and `MarkingStatus` overlap but are not the same set ("pending" means "could not read", not the observation state `pending`). Files that read job state: scan-marking-server.ts, scan-send-marking.ts, SQL functions; admin pages show JSON.
- DB enforcement: check constraints on state and blocked_reason; lease token compare after claim (`j.lease_token is distinct from p_token or lease_until<=now() or state not in (running,extracted)` -> `terminal`); budget admit under a global advisory lock; `unique(photo_id,attempt)` on dispatches.
- Impossible/unhandled: `finished` with `blocked_reason='attempts'` and pending items (Top finding 1). `queued` + `blocked_reason='off'` is retried every cron even when mode is off (route answers `off` first, so only after the switch is on). A job whose frame hash changed (`unavailable`) never recovers. `finished` + items with NULL model: not in team queue.
- Race / duplicates: one lease per photo (row lock + token); double charge window documented (lease lapses during a long paid call); `apply` skips items whose `owner_photo`/`result_version` moved (version compare), so a late apply cannot overwrite a later mark.
- What the user sees: results page "Page results": budget hold text only for `budget`; otherwise the page line (scan-marking-results.tsx:15-18: "This page has been marked." / "Our team is checking some answers on this page." / "Some answers on this page are not marked yet." / "This page is not marked yet." / "Your page is not marked yet." when no items). Stuck jobs look the same as not-started jobs.
- Existing tests: scan-marking.test.ts (63), scan-marking-server.test.ts, scan-marking-recovery.test.ts, scan-marking-launch/-family-mode/-d267-switch/-runtime-model tests; SQL probes scan_marking.sql, scan_marking_hosted.sql.
- Pure core already? Yes for the runner: `runScanMarking` is orchestration over `MarkingStore` with an in-memory store in tests. The SQL machine is NOT mirrored by a pure transition table.
- Value x risk: UX high (stuck/lying pages), DX high (3 stacked SQL wrappers, ~4 vocabularies), AX medium. Risk: money (budget), live paid calls, in-flight jobs; another lead is working here now.

### 6. Marking item (scan_marking_items.observation)
- Entity / storage: `public.scan_marking_items`: unique (workbook_id, printed_revision, page_id, item_id); `expected` jsonb (method code/parent/unscored/unavailable, mastery eligibility, scoredRegions); `observation` jsonb with `state` check in (`pending`,`scored`,`parent-pending`,`parent-checked`,`unscored`), `result` check right/wrong/blank/null, `certainty` certain/uncertain/not-read, `actor` system/parent/admin, `issue`; `result_version` (compare-and-set counter, check equals `observation.resultVersion`); `owner_photo` (the photo that claimed it for reading); `model`,`prompt`; `original_event` jsonb and `event_id` (see machine 7); `evidence_at`. - States (code names in scan-observation.ts:41): pending (not read, owner_photo may be set) -> scored (AI + code scored it, actor system) | stays pending (AI read it unsure: model set or certainty not `not-read`) -> parent-checked (a person set the result; actor `parent` or `admin`); parent-pending (old format a person marks); unscored (no mark by design).
