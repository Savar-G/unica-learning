Local PGlite checks do not prove hosted concurrent locks.

| Family | Rule |
| --- | --- |
| Customer: a live subscription, or a saved card that waits for the first workbook | Kept while it is a customer. |
| Former customer: only ended subscriptions in Stripe | Deleted 6 calendar months (UTC) after the latest subscription end (Stripe `ended_at`). Later tests do not change this deadline. |
| Free-test family: no subscription and no saved card, on the site's record or in Stripe | Deleted 12 calendar months (UTC) after the latest test activity. No test means no test-based deadline. Unchanged. |
| Any family, on a parent's request | Deleted at any time. Unchanged. |
| Stripe did not answer, or holds a state the rules do not know | Kept. The run reports `unknown` and is not ok. |

The rules are one pure function, `retentionDecision` in `src/lib/assessment/retention.ts`. Statuses `active`, `trialing`, `past_due`, `unpaid`, `paused` and `incomplete` are live. `canceled` is ended, and it needs `ended_at`; without it the family is unknown. `incomplete_expired` never started: it does not make a family a customer or a former customer. A status that Stripe adds later is unknown. A customer is certain whatever else Stripe holds, so a live subscription or a waiting card on any child's Stripe customer keeps the family. A saved card on a customer whose subscription ended does not wait for a first workbook.

The rules run twice. Only the second answer can start a deletion. The Node worker retries queued requests before it reads Stripe for unrelated families:

1. Before any freeze, read only. `family_retention_candidates` lists the queue, the due free-test families (`family_retention_due`, unchanged), and every non-admin family with Stripe history (a report card setup or a historical booking). It leaves out test families (`public.test_accounts`) unless they are in the queue (migration `20261101_retention_skip_test_families.sql`): their cards are often saved with a Stripe test key, which the live key cannot read, so they were unknown on every run. For each family with Stripe history, the worker reads every subscription page (`status: all`), the payment methods and the finished Checkout Sessions of each customer (`src/lib/retention-stripe.ts`). Each subscription page must have a Boolean `has_more`; a missing, null or invalid value makes the family unknown. Only `false` confirms the last page. A family that is kept or unknown is not claimed, so it is never frozen. Dry mode stops here.
2. After the freeze. The worker claims with `claim_family_retention`. For a former customer it passes the latest Stripe end date; under the parent row lock the database checks the end date, the 6-month deadline, a payment link, a card operation and admin membership again. A queued family and a free-test claim go through `claim_family_deletion` unchanged. In the checking phase, `checkFamilyPayments` reads every customer again before it changes anything in Stripe. A keep answer unfreezes the family (`decide_family_deletion` with keep) and changes nothing in Stripe. A delete answer closes open card setups, checks that none came back, and decides again from a second complete set of fresh reads. Unknown keeps the request and its fence for a later run, as before.

A succeeded SetupIntent is a card saved in the past. For a former customer it is settled history, like a canceled one, so the cleanup checkpoint can pass it. For any other family it still means a saved card, so the family stays. The rule of the first decision sets this; if the second decision has a different rule, the result is unknown.

## Process and concurrency

An admin opens a parent record and confirms its email. The route checks the signed-in user with Auth and the current admin registry. The session RPC checks admin membership again under a row lock. It refuses admin accounts and an active card operation. It writes a durable request and freezes the parent. The worker removes all objects in the exact private family folder before deleting Auth. The existing foreign keys remove the family tables. A final SQL check confirms that Auth, parent, and Storage records are absent before it removes the request.

Each family write takes a shared parent row lock through database triggers. A deletion request takes the exclusive parent lock and sets a persistent fence. A test, answer, or card save that wins the lock first changes eligibility before the claim. A write that loses the lock is rejected. The Storage trigger also fences secret-key uploads. Storage object insertion before the claim finishes first and enters the listing. Later insertion fails. A request accepted before admin revocation remains an authorized request; a request after revocation fails, including with the same session token.

Card creation holds the family across external Stripe requests. Retention cannot claim an active hold. After freezing a family, the worker deduplicates every tracked Stripe customer and checks up to four customers concurrently. Confirmed saved state cancels only the retention check and reopens the family. Unknown state keeps the checking request and the family fence. A timeout must not discard completed work or authorize deletion. An admin's explicit deletion does not cancel a subscription or delete Stripe payment history. It must be handled separately if requested. A parent's self-serve deletion stops each plan first; see [Self-serve delete](#self-serve-delete-556). Neither deletes Stripe payment history.

Checkout reads use Stripe's supported `open` and `complete` status filters. Each open page is expired, then the worker reads the first open page again. Expiration is durable progress. Historical expired sessions do not need traversal. Cleanup resumes across attempts. A completed canceled-intent checkpoint skips repeated cleanup for that customer. It does not establish that sessions or cards are clear. After all customers are prepared, a separate pass reads every customer's open sessions and current intent head. A changed head or open session invalidates preparation and keeps the request frozen. The final pass then reads completed sessions, payment methods, and subscriptions for every customer. No clear payment decision is stored between attempts. An interrupted final pass starts again with fresh reads for the full customer set.

SetupIntent listing has no status filter. The worker checks every page, including histories with more than 1,000 entries. A succeeded intent preserves the family. A processing or unrecognized state remains unknown. An unused intent in a supported cancelable state is canceled before traversal advances. The cursor records only immutable canceled intents. Partial traversal checks the current first page before resuming. Completed traversal is revalidated in the separate full-family pass; a new head or nonterminal entry resets preparation. A final fresh head check and current payment reads are required before deletion. Stripe states that operations on canceled SetupIntents fail. This terminal state permits durable traversal without caching a mutable clear result. See [SetupIntent listing](https://docs.stripe.com/api/setup_intents/list), [cancellation](https://docs.stripe.com/api/setup_intents/cancel), and [Checkout listing](https://docs.stripe.com/api/checkout/sessions/list).

Before each expiration or cancellation, a lease-guarded SQL operation record is written. A lost response leaves that record. A retry reads the resource's current state; it does not repeat an uncertain mutation. Only a fresh expired/canceled or complete/succeeded result can settle the record. Terminal records remain until the queue is removed, so a stale listing cannot cause a second mutation. Unknown reads and unresolved records block both the SQL deletion decision and reopening. A stale worker cannot settle a record or advance traversal after lease takeover. SetupIntents owned by Checkout cannot be canceled directly. If session expiration has not left the intent terminal, its state stays unknown. Do not force a clear result. Reconcile with Stripe before removing a hold. Live provider behavior and restricted-key cancellation access still require hosted verification.

A confirmed not-started operation is different from a lost remote result. If the journal request fails, or its response consumes the deadline before the Stripe method is invoked, the worker uses the separate control deadline to remove only its own pending record. The journal stores the originating lease token. `abandon_family_payment_operation` requires the same current, unexpired token, the same origin, and a null outcome. It cannot remove terminal records or a previous worker's uncertainty. The worker never invokes this recovery after calling a Stripe mutation. A failed recovery retains the record and the fence. A process crash with no reliable not-started result remains uncertain and requires reconciliation; age alone cannot release it.

The last test deadline uses the latest start, completion, or last answer across all children. It includes each stored answer's server timestamp, the facts section's start, and each facts answer's server timestamp. A committed answer changes eligibility even if its separate last-answer update fails. It adds 12 calendar months in UTC. An account with no test has no test-based deadline. Families with Stripe history follow the [retention rules](#retention-rules-191), and admin identities are excluded. The daily GitHub Actions worker (below) runs retention; it never sends emails or analytics. The Vercel schedule for `/api/retention` was removed at handover (#117), and the route itself on 2026-11-11. For a manual run, start the workflow by hand in mode `dry` (below).

Candidates use 100-row keyset pages. Images use 100-object pages in each folder. The worker removes each page, then reads offset zero again. Removed objects are durable progress. A stopped attempt resumes from the remaining objects without rebuilding the whole image tree. A short page is not an end marker. Every folder is read until empty. This avoids skipped objects when removal shifts the listing. Auth is deleted only after the entire family folder is empty. This also removes images with no answer reference and handles nested folders across children and tests.

Family UUIDs are normalized to lowercase before the request, Storage lookup, and Auth deletion. The daily job saves its last family before each attempt. The next run starts after that family and wraps once through the full candidate set. A slow first family cannot reset progress. The Node worker's family and work budgets are in [Foreground Node worker](#foreground-node-worker). The first attempt uses the current remaining time, including when the clock has advanced since the initial budget read. Later attempts require the initial full attempt budget before the cursor advances. This prevents a later family from repeatedly receiving only a short final attempt. Supabase requests use an abort signal. Each Stripe page and request uses the remaining timeout without network retries. Four customers are checked at once; current-state checking starts three reads per customer, so four concurrent customers can use twelve concurrent reads. At most four mutations run inside each customer. No call is scheduled after the deadline. Every started call is awaited, including when another call fails. Lease release and confirmed not-started recovery use the job's separate control deadline. An interrupted release leaves the lease for expiry and reclaim. A local timeout does not prove that Stripe canceled its remote work; the durable operation record retains this uncertainty.

## Recovery and deployment checks

Storage failure, Auth failure, or process termination leaves the request and the fence. A five-minute lease prevents duplicate workers. Normal failure releases the lease for a prompt retry. A stopped worker's expired lease can be reclaimed. A stale token cannot change or complete a job. Once the job enters deletion, no payment check can reopen the family. The daily job includes pending requests even when Auth has already been removed.

A process failure or caught Stripe failure during card creation can leave a `family_card_operations` hold. It has no automatic expiry. A known successful result releases only its own hold. A lost response keeps its hold even when the UI offers a later card link. Do not remove it on age alone. First stop the owning run. Reconcile the customer's idempotency reference, every Checkout session, and the saved-card state in Stripe. Record a succeeded setup in `card_setups`, or expire all open sessions and confirm no external request can resume. Then remove only that reconciled operation with `end_family_card_operation(token)`. A hold must block deletion while its result is unknown.

Before the final production rollout:

1. Apply the new migration with the migration tool. Verify the registry and probe the functions and triggers. Do not reapply the admin migration.
2. Deploy this code. Wait for old card-route invocations to finish before testing or enabling a retention run. The old implementation has no external card hold.
3. Test concurrent test starts, answers, card actions, and uploads against the claim in both orderings. Prove the full family scope and current-session admin revocation.
4. Test more than 1,000 candidate rows and private objects. Compare the full ID sets, not one page.
5. Inject Storage, Auth, and final queue failures. Test retry, lease expiry, and stale-token denial.
6. Check payment progress with eight customers, larger distinct-customer sets, and more than 1,000 sessions and SetupIntents. Verify current saved/processing state, supported cancellation permissions, remote lost results, pending records, and lease takeover. Do not run these tests against customer records.
7. Check the protected preview and deployed cron configuration. Before any bulk QA run, inspect the exact eligible set and prove that every eligible family is a fresh named QA family. Do not use production families as fixtures.

The normal production schedule must use the approved retention policy. The QA runner must not start a live bulk retention run while any eligible production family is present.

## Foreground Node worker

Build with `node scripts/build-retention-worker.mjs`. Run the foreground entry with `node --conditions=react-server .retention/worker.mjs --mode dry`. The default mode is dry. This mode reads every candidate page and, with the Stripe key, makes the read-only Stripe reads of step 1 in [Retention rules](#retention-rules-191), within the work budget. The job has a twenty-minute limit. Four setup steps have one-minute limits. Node allows fourteen minutes of work, up to ten minutes per family, and thirty seconds for final control cleanup. The Node worker first processes queued requests, in cursor order, before other candidates. It saves the cursor before each candidate's reads or deletion attempt. It processes each candidate before it starts another. This includes candidates that it keeps or cannot decide, so slow reads do not restart the same scan on every run. The first Node attempt uses its current remaining time. Later candidates require the reserved full family budget before cursor advancement. A deletion uses at most that budget and the time that remains after its reads. After a long failed attempt, the next invocation starts after that family within its queued or unqueued group. The worker renews checking and deleting leases once per minute, one request at a time. `renew_family_deletion_work` requires the current unexpired token. The existing deleting-only renewal stays in place. Stop and join the heartbeat before lease release. A completed lease must not continue to renew in the background.

SIGINT and SIGTERM stop new work. Supabase and Stripe use combined work, attempt and per-request abort signals. Work requests have a thirty-second limit. Control requests have a ten-second limit and an independent signal for release and confirmed not-started recovery. Await every started request. A local abort cannot prove a remote mutation stopped. Retain its journal and reconcile through fresh reads. Hard runner loss can prevent cleanup. The lease then expires; a later claim may resume, but renewal itself cannot reclaim. A new owner cannot erase a prior-origin uncertain record. Never abandon after invoking a mutation. GitHub cancellation can kill the process before graceful cleanup finishes. See [cancellation semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation).

### The confirmation code (#603)

The password of D-247 proved little: a signed-in session can set a new password with no current password (`security_update_password_require_reauthentication` is off), and a Google parent has none. So the delete needs something a stolen session alone does not have: the account's email. The screen flow is: press delete, read what stops and what stays, press "Email me a code", type the code and `DELETE`, confirm. The module is `src/lib/family-delete-code.ts`; migration `family_delete_code` adds `public.family_delete_codes`. The service-only functions are `begin_family_delete_code`, `read_family_delete_code` and `consume_family_delete_code`; none takes a time. Migration `family_delete_code_begin_db_clock` took the service role's execute off the two older functions that take a caller's time, `begin_family_delete_code(uuid, text, timestamptz, int, int, int, int, int)` and `spend_family_delete_code(uuid, text, timestamptz)`. They have no caller, and a later cleanup can remove them when a person can confirm the drop.

| Point | What the code does |
|---|---|
| Made and checked | On the server. The code is 6 random digits (`crypto.randomInt`). The browser never gets it |
| Stored | Only a salted scrypt hash, in `code_hash`. No copy: the email goes through `sendEmail` with no ledger, so `email_copies` holds nothing. The code is in no log. The email provider keeps the body it sent, but the code has ended by then |
| Life | 10 minutes, from the send. The database sets the end and decides when a code has ended, by its own clock (`clock_timestamp()`) after it holds the row lock. The app passes no time for either step, so a slow read or hash cannot pass an ended code, and a wrong app clock cannot make a code longer or shorter (migrations `family_delete_code_db_clock` and `family_delete_code_begin_db_clock`) |
| A new code | Replaces the old one, in the same row. The old one then answers "wrong" |
| Works once | The right code is spent when it is checked, by `consume_family_delete_code` under the row lock, so of two requests sent together one gets it. A failure in any later step needs a new code |
| Only this parent and action | The hash covers the action name, the parent's id and the address, so a stored hash is worth nothing for another parent, another address or another action |
| Wrong tries | `family_delete_attempts`, unchanged: counted before the check under a row lock, 5 tries, then 15 minutes locked, with the end of the lock in family time. Asking for a code never resets the count, and no code goes out during a lock. A code lives 10 minutes and a lock 15, so a lock always needs a new code |
| Sends | Per parent, under the row lock and by the database's clock: 3 in any hour and 6 in any day. A send counts when the provider refuses it too. When both limits are full, the answer gives the later of their two times, the first time a send can go |
| Address | `user.email` from the Auth server's answer for this session, and only when `email_confirmed_at` is set. Never the request and never `parents.email`. An account with no confirmed address is told to email us |
| The email | Says what the code is for, that it ends in 10 minutes, that a delete cannot be undone, and what to do if the parent did not ask. No child's name and no link. The code is not in the subject |
| Provider answers | Refused: the code is taken back and the parent is told. Unknown: the code stays live and the screen says it may have been sent |

Why not Supabase's email code. `signInWithOtp` is a sign-in: verifying it makes a session, and the code would prove sign-in and not this action, so a code asked for at sign-in could also confirm a delete. Its email is the "Magic link" template, which signup shows, so it could not say what it is for, and changing that template changes signup. Its life is `mailer_otp_exp`, 1 hour here and shared with signup. Supabase's reauthentication nonce is checked as part of a password update (read in `internal/api/user.go` of supabase/auth on 5 November 2026), and it has no check of its own to confirm another action. Our own code costs one table and keeps every point above.

Can a stolen session move the code to another address? Read on 5 November 2026: `mailer_secure_email_change_enabled` is true and `mailer_autoconfirm` is false in the project's Auth settings, and manual identity linking is off (`security_manual_linking_enabled` false). In supabase/auth, `UserUpdate` applies a new email directly only for an anonymous user with autoconfirm; every other user goes through `sendEmailChange`, which with this setting also sends a code to the current address. So a session alone cannot change the address: the change also needs the old mailbox, and until it is done `user.email` stays the old address. No route in this site changes an Auth email: the `updateUser` calls in `src` set only a password, and `src` has no `updateUserById` call. The hash covers the address, so a code sent before a change does not work after it. Not proved: this was read from the settings and the source. No live email change ran, because it would send email and leave a pending change on a test family.

What this does not stop: someone with both the session and the mailbox. A stolen session can also use up the sends or start the lock, which delays a real delete while that session lasts. Each code it asks for sends the parent an email.

`family_delete_codes` has no family write fence trigger, for the same reason as `family_delete_attempts`: it holds a hash, some times and no family data, and a parent must be able to confirm for a family the retention job froze. The row goes with the parent through the cascade.

### Why the plans stop first

A live subscription keeps a family only in the retention rules. A queued request skips them: the worker reads no plan state for it, and its restricted key cannot cancel a subscription. A request written while a plan runs would delete the family and leave Stripe charging the card. So the server stops every plan and reads every customer again before it writes the request. The customers come from `family_retention_cards`, so an old booking's customer counts; a booking with no matching customer stops the delete, and the parent is told to email us.

The cancel is `subscriptions.cancel` with `invoice_now=false` and `prorate=false`: at once, no refund and no last invoice. It uses the site's `STRIPE_SECRET_KEY`. Stripe's API reference says that a cancel stops automatic collection of the customer's finalized invoices by default, and that both parameters default to `false` (read on 5 November 2026).

A plan cannot start under a deletion. The admin's start route (`/api/admin/cards/[id]/start`) now holds the family across its Stripe call (`holdPlanStart`, with the card setup's id as the hold's id). A start that goes first makes the request answer `busy`, and the retry sees the new plan and stops it. A request that goes first makes the hold fail with `family_unavailable`, and no plan starts. A plan made by hand in the Stripe Dashboard is outside this rule.

The final plan read and the request are one span that no plan start can enter. Before that read, the delete takes its own hold (`begin_family_delete_hold`, a row of `family_delete_holds` with a random token), and `begin_family_card_operation` refuses with `family_unavailable` while it is live. The request (`request_parent_family_deletion_held`) is written only under that same token, with its lease still live, and with no card hold; it ends the hold in the same transaction. Both functions lock the parent row first (`for share` in the fence check, `for update` in the delete's), so a start and a delete see each other's rows in the order they ran. A start that ended before the hold has its plan in the read; one that holds a card row makes the delete answer `busy`.

Unlike a card hold, the delete hold has a lease of 5 minutes. A card hold may hide a Stripe object that a lost answer left behind, so it never expires. The delete hold covers no Stripe write of its own: a stop with a lost answer is settled by the read after it. So a server that dies while it holds blocks plan starts for at most 5 minutes, and blocks no retention run and no admin request. A request that names a lease that has ended is refused, because a plan may have started since the read; the parent's retry reads again. A failed step lets go of the hold at once (`end_family_delete_hold`, which ends only its own token's lease).

### What each failure leaves

| Failure | Family's data | Plans | Request and fence | What the parent sees |
|---|---|---|---|---|
| Wrong code, or locked | All there | Unchanged | None | Tries left, or the end of the lock |
| The code has ended or was used | All there | Unchanged | None | Ask for a new code (the try stays counted) |
| The code cannot be read or spent | All there | Unchanged | None | "We changed nothing" (the try stays counted, as in the PIN reset) |
| The code email is refused, or a send limit is reached | All there | Unchanged | None | The reason, with the time for a limit |
| Admin account, or a card hold | All there | Unchanged | None | Refusal; a hold says to try again |
| A customer or plan read fails, or an old booking has no match | All there | Unchanged | None | "We changed nothing" |
| The only stop fails | All there | Unchanged | None | "We deleted nothing" |
| A later stop fails | All there | Earlier plans ended; Stripe cannot undo this | None | How many plans stopped; try again. The team gets an email |
| The read after the stops fails, or finds a running plan | All there | As read | None | The same, and a retry stops what is left |
| The request write fails, or a hold appeared | All there | All ended | None, or written with its answer lost | The same. A retry writes the request once |
| The sign-out returns an error or throws, twice | Being deleted | All ended | Written | The confirmation, which says that every device signs out by the time the deletion finishes, not that it has. This device's cookies are cleared, and `src/proxy.ts` refuses the family's account pages, account APIs and desk to any access token still valid |
| The deletion stops after the request | Being deleted | All ended | Kept | The confirmation. The daily worker takes the family from the queue and resumes |
| A retention job froze the family first | Being deleted | All ended | Reason moves to `request`, so that job's `keep` cannot reopen it | The confirmation |

The deletion runs in `after()`, with `runFamilyDeletion`, and writes the copy without names before it removes Storage and Auth, as in every other path. A family with a queued request (reason `request`) gets no account page, account API or desk: `src/proxy.ts` reads `my_family_deletion_state` with the parent's session on those paths, sends pages to `/family-deleted` and answers the APIs with 410. A global sign-out ends the refresh tokens, but an access token already issued stays valid until it expires, and the database's write fence covers only writes, so this check is the one that covers reads, workbook PDFs among them. A failed read never lets the request through: the proxy then reads the request row in `family_deletions` with the secret key, and when that read fails too (or the key is not set) it answers 503, a plain "Please try again in a moment" page for pages and `{ ok: false, error: "unavailable" }` for the APIs. A working account costs one read; the second read happens only after a failure. The dashboard layout also sends a queued family there.

`/family-deleted` says that the plans stopped and no more charges follow only when `family_deletions.plans_stopped_at` is set, which only the parent's own flow writes, after its read under the hold. A signed-in parent is told only by their own `my_family_deletion_state`: `plans_stopped` gives "Your family's account is being deleted" with the plans line, `queued` gives the same title without it, and no request or a failed read gives the neutral words, never read from the cookie, because it may come from another family's delete on the same browser. After their own delete the session has ended, so the route sets the `unica_plans_stopped` cookie (HTTP only, path `/family-deleted`, one day) for that browser. The cookie proves neither who is reading nor that the deletion finished, so a signed-out visitor with it is told only about "a family" that asked on this browser: "In the last day, a family asked on this browser to delete its account. We stopped every workbook plan for that family, and that family will get no more charges," with the rest in "that family" words. Every other case gets the neutral words, titled "Deleting a family's account": "If you asked us to delete your family's account, we are deleting it."

Stripe's `customer.subscription.deleted` event can arrive while the family is fenced. The webhook's save is refused, it answers 500, and Stripe sends the event again; after the family is gone the customer has no match, and the webhook logs it and answers 204. A hold from a plan start whose Stripe answer was lost stays until the admin retries the start. To remove one by hand, reconcile the plan in Stripe, then call `end_family_card_operation` with the card setup's id.
