# Parent problem explanations (#675, D-299)

The parent selects Explain this problem beside a wrong answer on Page results. The API accepts only the item ID and mark version. The session supplies the parent. The service RPC resolves the child, book, immutable print, page, package and current canonical mark. It refuses other families, mismatched children, pending or unscored marks, unreadable answers and stale versions. The module also refuses invalid, unsupported and not-checked packages or a missing stored key. It does not mark a page or change a score.

The server withholds every explanation until the canonical page is complete. It checks each printed item for the same terminal states and exact scored-region set as pageCompletion, under the scan-family lock. The check runs on context, claim, admission, final save and cached read. A pending, missing, unavailable or parent-pending sibling cannot be bypassed by a direct request. Parent-checked and explicitly unscored siblings can complete the page under the existing rules.

The model receives four fields: stored question text, stored correct answer, the answer read from the page, and code-written steps. The steps come from code: a question with an operation sends its worked operation steps; a question filled from a step template (#971, `src/lib/question-package-steps.ts`) sends steps code writes from its stored template source (the sampled numbers, derived values and answer expression the checker recomputes), one line per operation, ending at the stored answer. They are worked out when the explanation is asked for; nothing is stored and a printed book is never rendered again. When code cannot write steps that end at the stored answer (a time, money in words, a choice between number sentences), it sends none. It receives no photo, identity, family record, profile or private file path. User wording and read answers stay JSON data under the system instruction. The output is one to four short steps and one sentence for the parent to say. Shape and length checks reject invalid output. Literal comparison signs remain valid in trusted keys, questions and explanation prose. Tag-shaped HTML and links are refused. React renders all accepted content as escaped text. The component renders text. Code displays the stored key separately. A fake test proves the data boundary. It does not prove that a real model follows the instruction on each adversarial input.

The context hash includes the prompt/schema protocol (`parent-problem-v2` since #971, so an explanation made without template steps is not read again; the price row keeps `parent-problem-v1`, as the model and limits did not change), canonical item identity, effective observation and mark version, full stored question/version, teaching and regions, and immutable print contract. A photo URL alone cannot select a cached explanation. The RPC checks the context at claim, admission, save and read. Corrections use the same family scan lock. A 20-second database lease serializes concurrent presses. A stale worker cannot save or release its successor. The module also checks abort and live session/release after blocking reads. Failed output never enters the success cache. A successful cached read still needs current ownership and mark eligibility.
